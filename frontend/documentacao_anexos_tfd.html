UNISISM · Módulo TFD (Face 4)

Guia de Integração para Desenvolvedores Backend - v1.0.0

1. Visão Geral das Alterações no Frontend

A tela de cadastro de passageiro e nova solicitação do regulador TFD (/tfd/solicitacoes/nova) foi aprimorada para atender a duas novas necessidades operacionais:

  • Auto-preenchimento de Município e UF: Ao abrir o formulário, o sistema identifica automaticamente a prefeitura vinculada ao regulador logado (via JWT) e preenche os campos correspondentes do passageiro para agilizar a digitação.
  • Gestão Integrada de Anexos: O regulador pode anexar múltiplos documentos antes de salvar. O frontend oferece três métodos de captura:
    1. Upload de arquivos locais (PDF, JPEG, PNG, WebP).
    2. Captura direta pela webcam (com stream e snapshot em tempo real).
    3. Simulador de scanner flatbed (gera um documento digitalizado contendo os dados do paciente preenchidos no formulário).
Comportamento de envio: O frontend realiza a operação de forma atômica e sequencial para o usuário. Ao clicar em "Cadastrar", o formulário principal é submetido e, logo após receber o ID da solicitação criada, o frontend envia os anexos um a um.

2. Fluxo de Comunicação Frontend ⇆ Backend

1
Consulta de Prefeitura do Regulador: O frontend chama GET /admin/prefeituras (ou infere a partir do escopo JWT no payload GET /auth/me) para obter os dados do município de origem (municipio, uf) e auto-preencher os dados do passageiro.
2
Criação da Solicitação Básica: Ao submeter o formulário, o frontend envia os dados clínicos e do paciente via POST /v1/tfd/solicitacoes. O backend realiza o cadastro e retorna o objeto criado contendo o ID e o número do protocolo.
3
Upload de Anexos: Para cada documento na fila, o frontend faz uma chamada POST /v1/tfd/solicitacoes/:id/anexos usando multipart/form-data contendo o arquivo físico e a tag de identificação do tipo.

4. Provisionamento Automático de Conta de Acesso (App do Paciente)

Quando o regulador do TFD insere os dados de um novo passageiro (paciente inline) no endpoint POST /v1/tfd/solicitacoes, o backend deve garantir o seguinte comportamento no banco de dados:

Garantia Transacional (All-or-Nothing): A criação do registro de Paciente e a criação da sua correspondente credencial de login para a Face 3 (/paciente-app) devem rodar sob a mesma transação de banco de dados. Se um falhar, toda a operação é revertida.

Fluxo de Cadastro pelo Backend:

  1. Cadastro/Upsert do Paciente: Salva ou atualiza a ficha cadastral do paciente na tabela principal do PEC municipal.
  2. Criação de Usuário (App do Paciente): Insere um registro de credencial na tabela de contas do paciente (Face 3).
    • Login / Identificador: CPF (apenas dígitos).
    • Senha Inicial: CPF (apenas dígitos).
    • Senha Provisória: true (força a alteração de senha no primeiro login via endpoint POST /paciente-app/auth/login antes de liberar o acesso).

5. Regras de Roteamento e Fila de Destino (Regulação SMS)

Durante a aprovação de um encaminhamento pelo regulador (POST /v1/encaminhamentos/:id/aprovar), o frontend permite direcionar o paciente para uma das três filas de destino:

  • SUS: Regulação tradicional da fila do Estado.
  • CENTRO_ESPECIALIDADES: Fila própria do Centro de Especialidades Municipal.
  • CEO: Fila própria do Centro de Especialidades Odontológicas.
Ocultação e Validação de Data Prevista: O campo agendamentoPrevisto (Data prevista do atendimento) é enviado apenas se o destino for SUS. Caso o encaminhamento vá para o CENTRO_ESPECIALIDADES ou CEO, a data prevista é ocultada no frontend e enviada como undefined para que o próprio Centro defina a data de acordo com sua agenda municipal interna.

Payload de Aprovação:

{
  "nota": "Paciente inserido na fila municipal...",
  "filaDestino": "SUS" | "CENTRO_ESPECIALIDADES" | "CEO",
  "agendamentoPrevisto": "2026-08-15" // Enviado opcionalmente apenas se filaDestino for "SUS"
}

6. Fluxo de Estados e Rota do Documento (Telas SMS)

Para evitar poluição visual no Centro de Comando da SMS, o ciclo de vida dos encaminhamentos é segregado de forma atômica entre três telas principais:

Tela no Menu Finalidade Filtros de Exibição (Status / Regras)
Solicitações (Inbox) Fila de entrada para análise do regulador. status IN ('AGUARDANDO_REGULACAO', 'PENDENCIA_DOCUMENTO')
Enviados (Fila de Espera) Casos aprovados aguardando agendamento ou parecer do SUS/Centros. status = 'APROVADO' AND respostaSUS IS NULL
Respostas (Ponto Final) Casos consolidados com retorno anexado. Fim da rota do documento. status = 'APROVADO' AND respostaSUS IS NOT NULL
