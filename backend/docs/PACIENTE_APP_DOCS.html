01Visão geral

O app do paciente (UNISISM-Paciente, Flutter) é a Face 3 do sistema. Atende o cidadão: ver encaminhamentos, baixar anexos, receber notificações, consultar dossiê médico (atendimentos + vacinas + exames), pedir TFD e ver banners da SMS.

2.2 Três prefixos coexistentes

O backend monta os mesmos handlers em três prefixos diferentes para satisfazer o contrato do app novo + manter retrocompatibilidade.

PrefixoStatusQuando usar
/auth/paciente/* RECOMENDADO Auth + perfil — contrato do app Flutter
/paciente/* RECOMENDADO Recursos (encaminhamentos, notificações, dossiê, etc.)
/paciente-app/* LEGADO Compat retro v0.17.x — todos os endpoints sob um único prefixo
Recomendação

Novos clientes devem usar /auth/paciente/* e /paciente/*. O /paciente-app/* continua funcionando indefinidamente, mas ficará marcado como deprecated em changelogs futuros.

3.6 CPF

  • App envia sempre só dígitos (53474131826)
  • Backend aceita formatado também e normaliza pra dígitos no banco
  • Backend devolve ambos: cpf (dígitos) + cpfFormatado (com pontuação)

3.7 Anti-enumeration global

Toda rota /paciente/:recurso/:id filtra por cpf = req.paciente.cpf (extraído do token). Recurso de outro paciente → 404 NOT_FOUND (não 403 — não vaza existência).

4.2POST /auth/paciente/refresh

POST /v1/auth/paciente/refresh PÚBLICO

Request

{ "refreshToken": "qCni7NtH_..." }

Response 200

Shape idêntico ao do login (com accessToken, refreshToken e expiresAt NOVOS).

Comportamento (rotação)

  1. Backend marca o refresh atual como usadoEm = now + link substituidoPorId
  2. Cria novo par (access + refresh)
  3. Retorna par novo
  4. Frontend DEVE substituir AMBOS os tokens no secure storage

Erros

HTTPcodeQuandoAção app
401REFRESH_TOKEN_INVALIDORefresh malformado ou inexistenteLimpa tokens → /login
401REFRESH_TOKEN_EXPIRADOPassou 30 dias sem usoLimpa → /login
401REFRESH_TOKEN_REVOGADOLogout anterior ou admin revogouLimpa → /login
401REFRESH_REUSE_DETECTEDToken vazado — cadeia revogadaAlerta segurança + /login
403CONTA_DESATIVADAAdmin desativouLimpa → /login
REFRESH_REUSE_DETECTED

Sinal de vazamento/clone do refresh. Backend revoga TODA a cadeia da conta (todos os refresh tokens vivos + sessões ativas). App deve mostrar alerta de segurança ao usuário antes de redirecionar pro login.

4.6POST /auth/paciente/esqueci-senha

POST /v1/auth/paciente/esqueci-senha PÚBLICO

Request

{ "cpf": "53474131826" }

Response 204 sempre (anti-enumeration — não vaza se CPF existe).

Side effects (se CPF existir + tiver email)

  1. Token opaco: crypto.randomBytes(32).toString('hex')
  2. tokenHash = SHA-256(token) armazenado em PacienteRecoveryToken
  3. TTL 30 min, uso único
  4. Email com link https://app.unisism.aguasbelas.pe.gov.br/redefinir?t=<token>
  5. Rate limit: 3 tentativas/h por CPF+IP, 5 req/15min/IP, 100 req/h/IP
  6. Audit log em todos os caminhos (existe/não-existe/expirado)

Defesas em profundidade

  • Timing-constant: MIN_MS aplicado quando CPF não existe
  • CPF checksum: bloqueia "11111111111" e similares
  • Cron de purge: tokens expirados/usados são deletados (TTL grace 24h)

14Fluxos críticos

14.1 🚨 Senha provisória (primeiro acesso)

  1. Backend auto-cria conta na consolidação do 1º encaminhamento da UBS: cpf, nome, senhaHash = bcrypt(cpf-digitos), ativo = true, senhaProvisoria = true.
  2. App login com cpf + senha=cpf-digitos
  3. Backend response paciente.senhaProvisoria=true
  4. App router força redirect pra /perfil/trocar-senha
  5. App tela bloqueante (sem botão X, PopScope bloqueia back)
  6. App chama POST /auth/paciente/trocar-senha
  7. Backend zera senhaProvisoria=false
  8. App chama GET /me confirmando
  9. App router libera, navega pra /home

14.2 🚨 Refresh transparente (401 → refresh → retry)

App tem interceptor Dio com single-flight:

  1. Request → 401 (não-auth path)
  2. Tem refresh token? → chama POST /auth/paciente/refresh
  3. Sucesso → retry original com novo access (marcado _retried p/ evitar loop)
  4. Falha (REUSE_DETECTED, EXPIRADO, etc.) → derruba sessão + vai pra /login

14.3 🚨 Anti-enumeration global

Toda rota /paciente/:recurso/:id deve:

  • Filtrar por cpf = req.paciente.cpf
  • Retornar 404 NOT_FOUND quando o recurso é de outro paciente
  • Nunca 403 (vaza existência)

14.4 🚨 Detecção de reuse de refresh

  1. App envia refresh A → backend rotaciona → emite refresh B
  2. Refresh A fica marcado usadoEm != null
  3. Se app envia refresh A de novo (ex: atacante clonou storage):
  4. Backend detecta reuse → revoga toda a cadeia da conta (todos os refresh + todas as sessões)
  5. Retorna 401 REFRESH_REUSE_DETECTED
  6. App deve mostrar alerta de segurança antes de redirecionar pro login
